# Технические детали работы протокола

## 1. Физический уровень: SX1278

### 1.1 Радиопараметры

**Базовый чип:** SX1278 (Semtech), half-duplex, sub-GHz ISM.

**Ключевые параметры конфигурации:**

|Параметр|Обозначение|Диапазон|Рекомендация для телеметрии|
|---|---|---|---|
|Spreading Factor|SF|6–12|7–9 (баланс дальность/скорость)|
|Bandwidth|BW|7.8–500 kHz|125 kHz|
|Coding Rate|CR|1–4 (4/5–4/8)|1 (4/5)|
|Preamble Length|n_preamble|6–65535|8|
|Payload Length|PL|1–255 байт|≤ 200|
|Header Mode|IH|0 (enabled) / 1 (implicit)|0|
|Low Data Rate Optimize|DE|0 / 1|1 при SF ≥ 11|
#### 1.1.1 
**Spreading Factor (SF)** — определяет, сколько чирпов (chirp) приходится на один символ. Чем выше SF, тем длиннее символ, тем больше энергии на бит, тем дальше достаёт сигнал и тем ниже скорость. Чем ниже SF, тем быстрее передача, но меньше дальность.

**Bandwidth (BW)** — ширина полосы канала. Чем шире полоса, тем выше скорость и тем ниже чувствительность приёмника. Чем уже полоса, тем дальше достаёт, но медленнее передача и больше время в эфире.

**Coding Rate (CR)** — доля полезных данных в общем потоке с помехоустойчивым кодированием. Чем выше CR, тем больше избыточности, тем устойчивее сигнал к помехам, но тем ниже реальная скорость.

**Preamble (n_preamble)** — длина преамбулы, последовательности символов перед пакетом. Нужна приёмнику для синхронизации. Чем длиннее преамбула, тем надёжнее приём, но тем больше времени занимает передача.

**Payload Length (PL)** — длина полезной нагрузки в байтах. Влияет на время в эфире: чем больше байт, тем дольше передача.

**Header Mode (IH)** — режим заголовка. При явном заголовке приёмник получает информацию о длине и CR пакета. При неявном — эти параметры должны быть известны заранее, что экономит байты, но требует фиксированной конфигурации.

**Low Data Rate Optimize (DE)** — флаг оптимизации для низких скоростей. Обязателен при высоких SF и узкой полосе, иначе дрейф частоты приведёт к ошибкам приёма.

**Half-duplex** — приём и передача одновременно невозможны. Пока узел передаёт, он не слышит других.
### 1.2 Time-on-Air (ToA): формула и расчёт

**Формула Semtech SX1278** [](https://www.alldatasheet.com/html-pdf/800241/SEMTECH/SX1278/9263/31/SX1278.html):

Символьная скорость:

**T_sym = 2^SF / BW**

Длительность преамбулы:

**T_preamble = (n_preamble + 4.25) × T_sym**

Количество символов payload:

**n_payload = 8 + max( ceil( (8×PL − 4×SF + 28 + 16×CRC − 20×IH) / (4×(SF − 2×DE)) ) × (CR + 4), 0 )**

Длительность payload:

**T_payload = n_payload × T_sym**

**ToA = T_preamble + T_payload**

### 1.3 Пример расчёта

**Конфигурация:** SF=8, BW=125 kHz, CR=4/5 (CR=1), n_preamble=8, PL=19 байт, CRC=1, IH=0, DE=0.

T_sym = 256 / 125000 = **2.048 ms**

T_preamble = (8 + 4.25) × 2.048 = **25.088 ms**[](https://patents.google.com/patent/CN111278033B/en#2)

n_payload = 8 + max( ceil( (8×19 − 32 + 28 + 16 − 0) / (4×8) ) × 5, 0 )  
= 8 + max( ceil( (152 − 32 + 28 + 16) / 32 ) × 5, 0 )  
= 8 + max( ceil(164 / 32) × 5, 0 )  
= 8 + max( 6 × 5, 0 )  
= 8 + 30 = **38 символов**

T_payload = 38 × 2.048 = **77.824 ms**

**ToA = 25.088 + 77.824 = 102.912 ms**

Практическое значение из исследования: **51.456 ms для 19 байт при 915 MHz, SF7** [](https://www.mdpi.com/1424-8220/25/19/6036#2). Расхождение объясняется разными SF и BW.

### 1.4 Duty Cycle и обязательный hold-off

**EU868:** 1% duty cycle на поддиапазоне. После передачи на время ToA узел должен молчать в 99 раз дольше [](https://ieeexplore.ieee.org/ielx8/6287639/10380310/10636160.pdf?tp=&arnumber=10636160&isnumber=10380310&ref=#6#1).

**Пример:** при ToA = 102.912 ms обязательный hold-off = 102.912 × 99 ≈ **10.19 секунды**.

**Для стационарных станций с передачей раз в час это не ограничение.** Для плотной сети — критично.

## 2. Формат пакета

### 2.1 Базовая структура (5-байтовый заголовок + payload)

Минимальный заголовок, проверенный на практике [](https://deepwiki.com/richardson2560/pressure-controller-esp32-base/5.1-binary-protocol-definition#1):

|Поле|Байт|Тип|Описание|
|---|---|---|---|
|dest_id|0|uint8|ID получателя (255 = broadcast)|
|src_id|1|uint8|ID отправителя|
|control|2|uint8|Тип кадра (биты 7-6) + флаги (биты 5-0)|
|ttl|3|uint8|Hop limit, декрементируется при пересылке|
|command|4|uint8|Идентификатор команды|

**Максимальный размер пакета:** 200 байт (ограничение LoRa E220) [](https://deepwiki.com/richardson2560/pressure-controller-esp32-base/5.1-binary-protocol-definition#1).

### 2.2 Control byte: типы кадров и флаги

**Типы кадров (биты 7-6):**

|Тип|Код|Описание|
|---|---|---|
|CMD|0x00|Команда|
|RESP|0x40|Ответ|
|ACK|0x80|Подтверждение|
|NACK|0xC0|Отрицательное подтверждение|

**Флаги (биты 5-0):**

|Флаг|Значение|Описание|
|---|---|---|
|ACK_REQUIRED|0x20|Требуется подтверждение|

### 2.3 TTL и предотвращение петель

**TTL:** инициализируется значением 16 [](https://deepwiki.com/richardson2560/pressure-controller-esp32-base/5.1-binary-protocol-definition#1). Каждый узел-роутер декрементирует TTL. При достижении 0 пакет отбрасывается.

**Дополнительно:** узлы ведут rolling buffer последних **30 messageID** для предотвращения петель и избыточного трафика [](https://www.mdpi.com/1424-8220/25/19/6036#2).

### 2.4 Command namespace

**Сетевые команды (0x00–0x0F):**

|Команда|Код|Описание|
|---|---|---|
|CMD_HELLO|0x01|Анонс соседства (broadcast)|
|CMD_ROUTE_AD|0x02|Анонс маршрута (broadcast)|

**Прикладные команды (0x10–0xFF):**

|Команда|Код|Описание|
|---|---|---|
|CMD_PING|0x10|Ping-запрос|
|CMD_GET_SENSOR_STATUS|0x20|Запрос статуса датчиков|
|CMD_SET_CONFIG|0x30|Установка конфигурации|
|CMD_UPDATE_RTC|0x40|Обновление RTC|
|CMD_MODULE_CTRL|0x41|Вкл/выкл модуля|

## 3. Маршрутизация

### 3.1 Автоматическое обнаружение соседей

**HelloTask:** периодически broadcast-ит сообщения HELLO для поддержания таблицы соседей [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1)

**Таблица соседей:** хранит ID соседа, качество канала (RSSI/SNR), время последнего контакта. Записи с истёкшим временем удаляются.

### 3.2 Поддержание таблицы маршрутов

**RoutingProtocolTask** удаляет истёкшие маршруты и соответствующие открытые соединения [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1)

**Академический протокол** использует distance-vector подход: маршрутные сообщения broadcast-ятся, соседи обновляют таблицы на основе полученной информации [](https://ieeexplore.ieee.org/abstract/document/10636160/references#references#1).

### 3.3 Path Discovery (по требованию)

**AODV-inspired подход** [](https://ieeexplore.ieee.org/document/11254006#1):

1. Sender хочет отправить unicast, но маршрута нет
    
2. Sender flood-ит ROUTE_REQ
    
3. Узел, знающий путь к получателю, отвечает ROUTE_RPL
    
4. Sender записывает next_hop в route cache
    
5. Последующие пакеты идут напрямую
    

**Оптимизация:** next-hop caching + multi-route memory + weight-based route selection снижают routing latency на **19 µs**, end-to-end latency на **796.44 s** по сравнению с классическим AODV [](https://ieeexplore.ieee.org/document/11254006#1).

### 3.4 Forwarding (пересылка)

**ReceiveTask** (высший приоритет): принимает пакеты, помещает в receive queue [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1).

**ProcessTask:** проверяет destination.

- Если пакет адресован локальному приложению → application-delivery queue.
    
- Иначе → send-queue для передачи следующему hop.
    

**SentTask:** извлекает из send-queue и передаёт через LoRa.

### 3.5 Self-Healing

При отказе узла сеть автоматически перестраивается [](https://www.mdpi.com/1424-8220/25/19/6036#2):

**Packet Recovery Ratio (PRR):** отношение восстановленных пакетов к ожидаемым при отказе.

**Эксперимент:** при отключении узла D коммуникация между A и E сохранилась в обоих направлениях через альтернативные маршруты [](https://www.mdpi.com/1424-8220/25/19/6036#2).

## 4. Надёжность

### 4.1 End-to-End ACK

**Reliable transfer mode** [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1):

1. Приложение вызывает `sendReliable()`
    
2. Сообщение передаётся с end-to-end подтверждением
    
3. Промежуточные узлы выполняют базовую обработку (forwarding)
    
4. Только source и destination участвуют в механизме надёжности
    

### 4.2 Hop-by-Hop ACK

**Total Retries** метрика: сумма всех попыток retransmission на каждом hop до получения ACK [](https://www.mdpi.com/1424-8220/25/19/6036#2)

### 4.3 Fragmentation (фрагментация)

При превышении `LM_MAX_PACKET_SIZE` [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1):

1. Сообщение разбивается на фрагменты
    
2. Каждый фрагмент передаётся отдельным пакетом
    
3. Destination собирает фрагменты
    
4. Собранное сообщение передаётся приложению
    

**Timeout reassembly:** при потере фрагмента менеджер очередей обрабатывает таймаут [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1).

## 5. Управление очередями (FreeRTOS)

### 5.1 Архитектура задач

|Задача|Приоритет|Функция|
|---|---|---|
|ReceiveTask|Highest|Приём из LoRa, помещение в receive queue|
|ProcessTask|High|Маршрутизация, определение destination|
|RoutingTask|Medium|Route discovery, neighbor table|
|SentTask|Medium|Передача из send-queue|
|QueueManagerTask|Low|Управление очередями, таймауты|

**ReceiveTask** имеет высший приоритет для предотвращения потери пакетов при временной перегрузке [](https://www.sciencedirect.com/science/article/pii/S2352711026000646?fr=RR-2&ref=pdf_download&rr=a0ae37fac819ce05#1).

### 5.2 Очереди

- **received-packets queue** — входящие пакеты
    
- **application-delivery queue** — пакеты, адресованные локальному приложению
    
- **send-queue** — пакеты для передачи следующему hop
    
- **large-message queues** — для фрагментированных сообщений

## 6. Энергопотребление
### 6.1 Реальные измерения
### 6.2 Решение: отключение NRESET

**Проблема:** при входе ESP32 в deep sleep на пине NRESET LoRa-модуля может появиться импульс, который **будит SX1278** [](https://forum.arduino.cc/t/power-consumption-issue/1249483/5).

**Решение:** физически отключить пин NRESET от ESP32. Модуль работает без него, а `LoRa.sleep()` начинает работать корректно [](https://forum.arduino.cc/t/power-consumption-issue/1249483/5).

### 6.3 Дополнительные меры

**Power latch circuit** [](https://forum.arduino.cc/t/esp32-lora-mp3-energy-consumption/1409550/3#1): вместо deep sleep — полное отключение ESP32 через внешний latch. ESP32 потребляет **ноль ампер** в выключенном состоянии.

**RTC (например, DS3231):** периодически включает ESP32 для передачи данных [](https://forum.arduino.cc/t/esp32-lora-mp3-energy-consumption/1409550/3#1).

## 7. Ограничения SX1278

### 7.1 Half-Duplex

SX1278 — **half-duplex** трансивер. Одновременный приём и передача невозможны [](https://ieeexplore.ieee.org/ielx8/6287639/10380310/10636160.pdf?tp=&arnumber=10636160&isnumber=10380310&ref=#6#1).

**Следствие:** узел не может слышать других, пока передаёт. При плотной сети это создаёт коллизии.

### 7.2 Единственный канал и SF

SX1278 работает на **одном канале с одним SF** одновременно [](https://ieeexplore.ieee.org/ielx8/6287639/10380310/10636160.pdf?tp=&arnumber=10636160&isnumber=10380310&ref=#6#1). Multi-channel возможен только с несколькими трансиверами или переключением.

### 7.3 Duty Cycle

**EU868:** 1% [](https://ieeexplore.ieee.org/ielx8/6287639/10380310/10636160.pdf?tp=&arnumber=10636160&isnumber=10380310&ref=#6#1). При ToA ~100 ms обязательный hold-off ~10 секунд.

**Для телеметрии раз в час:** не проблема.

**Для текстовых сообщений в реальном времени:** критическое ограничение при плотной сети.
